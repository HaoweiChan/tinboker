# Old-episode backfill

How to ingest a channel's back catalogue, and how to generate the content for it with
a Claude session instead of OpenRouter.

Two halves that run in different places:

| Half | What it does | Where it runs | Cost |
|---|---|---|---|
| **Ingest** | feed → mp3 → Whisper transcript → episode row | **VPS only** (writes the media tree) | Groq STT per episode |
| **Content** | transcript → summary / insights / tickers / slides | **anywhere** (reads artifacts over HTTPS) | OpenRouter, or a Claude session via the `podcast_regen` MCP server |

---

## The floor: 2020-02-27

Gooaye 股癌 EP1, read from the show's canonical RSS (`feeds.soundon.fm/podcasts/954689a5-…`,
last `<item>`, `pubDate: Thu, 27 Feb 2020 19:51:55 GMT`). Several feeds reach further
back than that — M觀點's goes to 2019-11-10 — and nothing older than 股癌 EP1 is in
scope, so every backfill run passes `--since 2020-02-27`.

## Ingest

```bash
cd pipelines/services/podcast
python main.py --config podcasts_tw.json --show "Gooaye 股癌" \
    --fill-limit --since 2020-02-27 --no-store-audio [--skip-summarize]
```

- `--fill-limit` walks the feed newest-first, skips episodes already complete, and
  takes the show's `limit` unprocessed ones. Re-running it therefore walks backwards
  through history — that is the reverse-chronological backfill, no new code.
- `--since` drops everything published before the floor. Undated feed entries are kept.
- `--no-store-audio` keeps the MP3 out of the media tree. See *Disk* below.
- `--skip-summarize` stops after transcribe + persist, leaving the LLM content to a
  Claude session. Omit it to have OpenRouter write the content as usual.

`--skip-summarize` and `--no-store-audio` change what "already processed" means —
`required_artifact_urls()` in `pipelines/services/podcast/src/pipeline/utils.py` derives
that set from the mode. Without it a transcript-only episode reads as unprocessed
forever and is re-downloaded and re-transcribed on every run.

### Disk

The media tree is 105 GB of a 251 GB disk with 108 GB free, and **103 GB of it is
MP3** — 3,753 files averaging 27.8 MiB, against 177 KB for a transcript. Keeping audio
caps the backfill at roughly 2,100 episodes (20% free-space floor); dropping it makes
disk a non-issue at ~1 GB for the whole catalogue.

Dropping audio is safe for backfilled episodes: the player prefers the Spotify embed
and only falls back to `mp3_public_url` when an episode has no Spotify URI
(`frontend/src/components/player/GlobalPlayer.tsx:319-338`). The one path that needs a
stored MP3 is a `--rerun-from transcribe` re-transcription, which re-downloads it from
the media host (`src/pipeline/steps/download.py:48-76`) — so do not re-transcribe an
episode ingested with `--no-store-audio`; re-ingest it instead.

## Content, generated by a Claude session

The `podcast_regen` MCP server (registered in the repo-root `.mcp.json`) hands a session
the pipeline's real prompts and runs the pipeline's real glue and write paths, so the
result is byte-identical in shape to an OpenRouter run — enforced by
`test_episode_doc_parity_pipeline_vs_regen`. Flow per episode:

`list_regen_candidates(only_placeholder=True)` → `start_regen` → for each of
`extractor`, `writer`, `key_insights`, `ticker_extractor`: `get_role_prompt` → generate →
`submit_role` → `preview_regen` → `commit_regen`.

`--skip-summarize` produces exactly what that queue looks for: an episode with a
transcript and no content.

## Sequencing — the one that can cause harm

**Do not widen `RELEASE_EPISODE_MAX_AGE_DAYS` while a backfill batch is still unscanned
by the notification producer.**

Backfilling on its own is safe. `released_at_ms` resolves from the feed's
`datePublished` before anything else (`src/models/podcast_models.py:119-146`), so a 2020
episode ingested today carries a 2020 release time, fails the producer's release-date
cutoff (`backend/src/services/notification_producer.py:103-119`), and the high-water
mark advances past it having sent nothing.

The mark itself is `first_seen_at`, which is stamped `now()` on insert — so every
backfilled row does cross it. If the window is widened *before* the producer's next
cycle (10 min), those rows stop being filtered and the platform fires new-episode,
stock-mention and topic-mention notifications for the entire batch.

Order: backfill → wait for a producer cycle → then widen the flag.

Syndication (方格子/Substack) and Threads/FB autopublish are unaffected either way; both
keep their own release-date-keyed age limits (`SYNDICATE_MAX_AGE_DAYS` default 7,
`threads_max_age_days`).

### What widening the window exposes

`RELEASE_EPISODE_MAX_AGE_DAYS=60` in all three environments today, so only ~301 of the
4,551 stored episodes have public pages. Removing the cutoff would expose ~4,476 of the
existing store before any backfill lands. Note that `get_recent_episodes` and the
sector/board/tag scans (`backend/src/services/podcast.py:888-915, 1440, 2307, 2380`)
fetch the whole episodes table and apply the cutoff in Python — the backfill roughly
doubles that scan cost on every hourly refresh and cache miss, which is the same shape
as the July 2026 billing incident. Budget for it.
